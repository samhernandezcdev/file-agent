## Minor

### m1. No `PolicyDecision` domain invariant tests

`tests/domain/test_proposal.py` thoroughly tests `FileProposal` invariants (confidence bounds, frozen mutation, empty reasons, etc.), but there is no analogous `tests/domain/test_policy.py` for `PolicyDecision`. The invariants are enforced by Pydantic `Field` constraints (`ge=0.0`, `le=1.0`, `min_length=1`) and `normalize_to_utc`, but no test proves they reject malformed input.

**Affected code**: `domain/policy.py:37-53` (PolicyDecision fields)

**Why it matters**: If a future refactor accidentally weakens a constraint (e.g., removing `ge=0.0` from `proposal_confidence`), no test would catch it. A minimal invariant test file would be defensive documentation.

### m2. Persistence test always produces AUTO

`test_persistence_integration.py` uses `make_proposal()` with default parameters (`DOCUMENT + DOCUMENTS + confidence=1.0`), which always yields `AUTO`. There is no persistence round-trip test for a `REVIEW` decision. The event payload serialization for `REVIEW` is correct (the `decision` field is just a string), but an explicit test would guard against future regressions.

**Affected code**: `test_persistence_integration.py:30-42` (default proposal)

**Why it matters**: Low — the serialization logic is the same for all `PolicyOutcome` values. But a `REVIEW` persistence test would complete the coverage matrix.

### m3. No test proving BLOCK is never produced

`PolicyOutcome.BLOCK` exists in the enum and the docstring states "no v1 rule produces it," but no test asserts `BLOCK` is unreachable. A test like `assert all(evaluate_for(p).decision is not PolicyOutcome.BLOCK for p in ...)` across a representative set of inputs would be defensive documentation.

**Affected code**: `domain/policy.py:24` (BLOCK enum member), `engine.py` (no BLOCK branch)

**Why it matters**: Low — the engine code clearly has no BLOCK branch. But a test would guard against accidental BLOCK production if a future rule is added carelessly.

### m4. No test for a hypothetical future `PolicyOutcome` member

The engine's `evaluate()` method uses `if/elif/else` with a final `else: REVIEW`. A future `PolicyOutcome` member (e.g., `DEFER`) added to the enum but not handled by the engine would silently produce `REVIEW` — which is the correct default-deny behavior. But no test verifies this structural property.

**Affected code**: `engine.py:46-100` (if/elif/else chain)

**Why it matters**: Cosmetic — the default-deny design is correct by construction. A test would be documentary.

### m5. `BLOCK` semantics could use a stronger docstring

`PolicyOutcome.BLOCK` docstring says "an explicit prohibition, not merely uncertainty requiring a human decision." This is correct but could explicitly state "never produced by rules-v1" to prevent a future developer from assuming BLOCK is used.

**Affected code**: `domain/policy.py:17-20`

**Why it matters**: Cosmetic — the engine code and rules.py comment both state BLOCK is not produced. A docstring强化 would be defensive.

## Architectural observations

1. **AUTO default-deny is correct and verified.** The engine uses a strict if/elif/else chain: no destination → REVIEW, EXECUTABLE → REVIEW, pair not on allowlist → REVIEW, confidence below threshold → REVIEW. AUTO is only reachable when all four gates pass. The `AUTO_ELIGIBLE_PAIRS` frozenset is defined independently of `proposal_engine.DESTINATION_FOR_CATEGORY` (rules.py:7 comment), so proposal mapping and policy authorization are separate responsibilities.

2. **EXECUTABLE override is unconditional.** `proposal.category is FileCategory.EXECUTABLE` is checked before the allowlist and confidence gates. Even `EXECUTABLE + EXECUTABLES + confidence=1.0` yields REVIEW. No confidence value can bypass this override. This is the primary proof of `confidence != permission`.

3. **BLOCK is reserved and unreachable.** `PolicyOutcome.BLOCK` exists in the enum but no code path in `engine.py` produces it. The rules.py comment explicitly states it's deliberately absent. The docstring correctly describes BLOCK as "stronger than REVIEW: an explicit prohibition." No test accidentally expects BLOCK for uncertainty.

4. **AUTO semantics are honest.** AUTO means only "eligible for future automatic execution, subject to later execution/runtime safety checks." The reasons text says "destination category exists," "pair is on the allowlist," and "confidence satisfies the threshold." There is no execution callback, no path resolution, no TransactionEngine dependency, no "moved" or "approved" language.

5. **REVIEW is purely semantic.** REVIEW means "policy does not permit automatic execution." There is no `00_Revisar` creation, no physical review path, no quarantine. The reasons text says "automatic execution is not eligible" — informational only.

6. **PolicyDecision invariants are sound.** Frozen model, extra fields forbidden, UUID identity, `proposal_id` required, `file_id` required, non-empty reasons, timezone-aware normalized UTC `evaluated_at`, non-empty `policy_engine_id` and `proposal_engine_id`, `proposal_confidence` in [0.0, 1.0]. The `source_category` and `destination_category` fields capture the classification/destination snapshot for provenance.

7. **Structured provenance is complete.** Every `PolicyDecision` captures: `proposal_id`, `file_id`, `source_category`, `destination_category`, `proposal_confidence`, `proposal_engine_id`, `policy_engine_id`. Human-readable reasons are not the only representation. The `POLICY_EVALUATED` event payload includes all these fields.

8. **Event semantics are correct.** `entity_type=EntityType.POLICY_DECISION`, `entity_id=decision.id`, `timestamp=decision.evaluated_at`. The payload includes `proposal_id`, `file_id`, `decision`, `source_category`, `destination_category`, `proposal_confidence`, `proposal_engine_id`, `policy_engine_id`, and `reasons`. Repeated evaluation appends new events (fresh `decision.id`).

9. **Re-evaluation is safe.** Evaluating the same `FileProposal` multiple times creates fresh `PolicyDecision` IDs with identical decision content. No mutation of previous decisions. Coexistence in persistence is proven by `test_repeated_evaluations_append_history_not_overwrite`.

10. **Determinism is structural.** Same `FileProposal` + same `policy_engine_id` + same clock = identical `PolicyDecision` content (excluding `id`). The test `test_full_result_is_deterministic_with_fixed_clock` compares `model_dump(exclude={"id"})`, covering all fields including `proposal_id`, `file_id`, `source_category`, `destination_category`, `proposal_confidence`, `proposal_engine_id`, `evaluated_at`, and `reasons`.

11. **Threshold behavior is correct.** `AUTO_CONFIDENCE_THRESHOLD = 1.0` is applied with `>=`, so exactly 1.0 qualifies and anything below (0.999..., 0.5, 0.0) yields REVIEW. No floating-point normalization or silent clamping occurs.

12. **Zero filesystem I/O — verified.** The AST guardrail (`test_no_filesystem_access.py`) checks every `.py` in `src/file_agent/policy_engine/` for forbidden imports and calls. The engine imports only `collections.abc`, `datetime`, and `file_agent.*` modules.

13. **No naming transformation.** The engine never sets `proposed_name`. The `FileProposal` is consumed read-only. No helper code or dead code anticipates filename cleanup.

14. **Independence from FA-006 is explicit.** `AUTO_ELIGIBLE_PAIRS` is a `frozenset` defined in `rules.py`, not imported from or derived from `proposal_engine.DESTINATION_FOR_CATEGORY`. The docstring states: "proposal mapping and policy authorization are separate responsibilities that may intentionally diverge."

## Summary

FA-007 is a clean, minimal implementation that correctly evaluates proposals against fixed policy rules with default-deny AUTO eligibility. The EXECUTABLE override is the primary proof that `confidence != permission`. BLOCK is properly reserved. No filesystem I/O, no execution, no naming. The architecture boundary is well-maintained. The minor issues — missing `PolicyDecision` invariant tests, no REVIEW persistence test, no BLOCK-reachability assertion — are defensive documentation gaps that don't affect correctness or safety.
