## Minor

### m1. No test for `proposed_destination_category=None` round-trip through persistence

`test_persistence_integration.py` always creates classifications with mapped categories (`DOCUMENT`), so `proposed_destination_category` is never `None` in persistence tests. The payload correctly handles `None` (`engine.py:94-98`), but there's no test proving a `None` value survives serialization and deserialization through `FileAgentStore.record_event()` → `list_events()`.

**Affected code**: `engine.py:94-98` (conditional serialization), `test_persistence_integration.py`

**Why it matters**: A regression in the conditional serialization would silently produce a payload with `proposed_destination_category` missing or as a wrong type. An explicit round-trip test with `OTHER` or `UNKNOWN` would catch this.

### m2. Event entity_id refers to proposal, not file — lookup by file requires payload scan

`proposal_event()` sets `entity_id=proposal.id`, so `store.list_events(EntityType.PROPOSAL, proposal.id)` retrieves events for a specific proposal. There is no index-friendly way to retrieve all proposals for a given file — the `file_id` is buried in the JSON payload.

This is a correct design choice (each proposal is its own entity), but it means a future caller wanting "all proposals for file X" must scan all `PROPOSAL_CREATED` events and filter by `payload["file_id"]`. Worth documenting as an architectural note for FA-007.

**Affected code**: `engine.py:89` (`entity_id=proposal.id`)

**Why it matters**: Low — the current test `test_repeated_proposals_append_history_not_overwrite` correctly proves append-only semantics per proposal. The file-level lookup gap is a future concern, not a correctness issue.

### m3. `source_classification_confidence` divergence not tested for mapped categories

`test_unknown_and_other.py::test_other_produces_no_destination_but_preserves_source_confidence` proves `source_classification_confidence=1.0` while `confidence=0.0` for `OTHER`. But there's no test explicitly verifying that for mapped categories, `confidence == source_classification_confidence` (they're equal by construction in `engine.py:57`, but a test would guard against future divergence).

**Affected code**: `engine.py:57` (`confidence = classification.confidence`)

**Why it matters**: Low — the current code is correct. A test would be defensive documentation.

### m4. `DestinationCategory.AUDIO` is singular while others are plural

`DestinationCategory` uses `AUDIO` (singular) alongside `DOCUMENTS`, `IMAGES`, `ARCHIVES`, `EXECUTABLES` (plural). `CODE` is also singular. The naming is semantically correct ("audio" is uncountable in English; "code" is a mass noun), but the inconsistency could surprise a future caller expecting uniform pluralization.

**Affected code**: `proposal.py:43-49` (DestinationCategory enum), `rules.py:17-26` (mapping table)

**Why it matters**: Cosmetic. The values are stable and the inconsistency is linguistically justified. Worth noting only for future API consumers.

### m5. Determinism test excludes `id` but doesn't verify `source_classification_confidence`

`test_full_result_is_deterministic_with_fixed_clock` compares `model_dump(exclude={"id"})`, which includes all fields except `id`. This implicitly covers `source_classification_confidence` and `source_classifier_id`. But the test assertion doesn't name these fields explicitly — a future refactor that adds a non-deterministic field (e.g., a random nonce) would pass the existing test if it's added to the exclude set.

**Affected code**: `test_determinism.py:59`

**Why it matters**: Cosmetic. The test is correct today. Explicit field assertions would be more resilient to future changes.

## Architectural observations

1. **Zero filesystem I/O — verified.** The AST guardrail (`test_no_filesystem_access.py`) checks every `.py` in `src/file_agent/proposal_engine/` for forbidden imports (`os`, `shutil`, `io`), forbidden calls (`open()`), and forbidden `Path` methods. The engine imports only `collections.abc`, `datetime`, and `file_agent.*` modules — no I/O-capable dependencies.

2. **Policy-free design.** The engine maps `FileCategory` → `DestinationCategory` through a fixed table. No permission semantics, no authorization rules, no safety approval, no review requirements. The `FileCategory.EXECUTABLE` docstring explicitly states it "exists to preserve a distinct signal for a future policy layer" — the proposal engine does not implement any such policy. EXECUTABLE is handled identically to DOCUMENT, IMAGE, and every other mapped category.

3. **DestinationCategory is purely logical.** It's a `str` enum with values like `"documents"`, `"images"`, `"executable"` — not filesystem paths, not arbitrary strings. The engine never resolves it into an absolute/relative path. No organization root exists. No destination directory existence check occurs. The enum docstring explicitly states this is "deliberately distinct from `proposed_destination` (an absolute path, reserved for a future organization-root-aware producer)."

4. **FA-001 invariants preserved.** `proposed_destination` retains its `Path | None` type with `ensure_absolute_path` validator — FA-006 always leaves it `None`. `proposed_name` is always `None`. The `test_naming.py` parametrized test proves this for all 9 `FileCategory` values. No FA-001 invariant has been weakened.

5. **Source vs destination semantics are unambiguous.** `FileProposal.category` = source `FileCategory` (the classification). `FileProposal.proposed_destination_category` = `DestinationCategory | None` (the logical destination). The docstrings are explicit: `category` is "the classification category this proposal is based on — not an independent proposal-specific taxonomy." The event payload includes both as separate fields. Tests verify the distinction.

6. **Structured classification provenance.** Every proposal preserves `source_classification_confidence` (verbatim from the `ClassificationResult`), `source_classifier_id` (which classifier produced the classification), and `category` (the source `FileCategory`). These are machine-readable fields, not just prose in `reasons`. `test_provenance.py` proves these match the input classification, and that `source_classifier_id` is not hardcoded to `PROPOSAL_ENGINE_ID`.

7. **Confidence semantics are honest.** When a destination exists: `proposal.confidence == source_classification_confidence`. When no destination exists: `confidence = 0.0`. The `source_classification_confidence` is always preserved verbatim, so a confident `OTHER` classification (confidence=1.0) doesn't lose its signal just because no destination was proposed. The docstring explicitly states: "Not an independently computed probabilistic model — never authorization to act."

8. **UNKNOWN and OTHER are correctly differentiated.** Both produce `proposed_destination_category=None`, `proposed_destination=None`, `proposed_name=None`, `confidence=0.0`. But `source_classification_confidence` preserves the distinction: UNKNOWN has 0.0, OTHER can have 1.0. Reasons text also differs. Neither becomes "human review required" — that's FA-007's concern.

9. **Event persistence is a thin composition boundary.** `proposal_event()` creates a `DomainEvent` with `EventType.PROPOSAL_CREATED`, `entity_type=EntityType.PROPOSAL`, `entity_id=proposal.id`. The package has zero dependency on `file_agent.persistence`. Repeated proposals for the same file get different `proposal.id` values, so they append as separate historical events. The payload includes all structured data needed to reconstruct the proposal meaningfully.

10. **Determinism is structural.** Same `ClassificationResult` + same rule table + same clock = identical `FileProposal` (excluding `id`, which is a fresh UUID per construction — this is correct and documented). The `fixed_clock` fixture enables full determinism testing including `created_at`. No randomness, no external state, no filesystem state.

11. **Mapping table is correct.** All 7 primary `FileCategory` values map to a `DestinationCategory`. `OTHER` and `UNKNOWN` are deliberately absent (comment in `rules.py:25`). No duplicates, no unreachable entries. The naming convention (singular mass nouns for AUDIO/CODE, plurals for countable categories) is linguistically consistent.

---

## Summary

FA-006 is a clean, minimal implementation that correctly answers "what logical destination would be proposed?" without overstepping into policy, authorization, or filesystem resolution. The architecture boundary is well-maintained, the invariants are sound, and the test coverage is thorough. The minor issues — missing `None`-destination persistence test, singular AUDIO/CODE naming, and defensive confidence-equality test — don't affect correctness or safety.
