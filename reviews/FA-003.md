## Minor

### m1. `resolve_for_containment()` silently accepts paths with non-existent intermediate directories

- **severity**: minor
- **affected file**: `src/file_agent/hasher/_paths.py:19-33`
- **concrete problem**: `path.resolve(strict=False)` resolves the path as far as possible, even if intermediate directories don't exist. A path like `C:\sandbox\nonexistent_dir\..\file.txt` would resolve to `C:\sandbox\file.txt` (normalizing the `..`), pass containment, and then `os.stat()` would return `NOT_FOUND` for the actual target. This is correct behavior, but the resolution step might produce a path that doesn't correspond to any filesystem object the caller intended.
- **why it matters**: A `DiscoveredFile` with a path containing `..` segments (e.g., `C:\sandbox\sub\..\file.txt`) would pass containment, resolve to `C:\sandbox\file.txt`, and hash the wrong file if `C:\sandbox\file.txt` exists. However, the scanner stores paths from `os.scandir()`, which don't contain `..` segments, so this is unlikely in practice.
- **recommended fix**: No code change needed for FA-003. The scanner guarantees clean paths. Document that `resolve_for_containment()` normalizes `..` segments.

### m2. Check A doesn't compare st_dev/st_ino with the FA-002 observation

- **severity**: minor
- **affected file**: `src/file_agent/hasher/hasher.py:148-161`
- **concrete problem**: Check A compares metadata (size, timestamps) between the pre-open stat and the FA-002 observation. But the FA-002 observation doesn't include st_dev/st_ino, so there's no way to verify that the file is the same inode as the scanner observed. The st_dev/st_ino comparison only happens between checkpoint1 and checkpoint2 (pre-open vs post-open).
- **why it matters**: If a file is replaced with a different file that has identical metadata (same size, same timestamps), the hasher would accept it. This is effectively impossible on most filesystems (new files get new inodes), but not theoretically impossible with hard links or synthetic filesystems.
- **recommended fix**: No code change needed for FA-003. The scanner's observation is metadata-only (by design), and the hasher's identity chain (checkpoint1→checkpoint2→checkpoint3) is sufficient. Document this as a known limitation of the metadata-only observation model.

### m3. `_IdentitySnapshot.st_mtime` and `st_ctime` are `float`, not `datetime`

- **severity**: minor
- **affected file**: `src/file_agent/hasher/hasher.py:31-48`
- **concrete problem**: `_IdentitySnapshot` stores `st_mtime` and `st_ctime` as `float` (raw OS timestamps), while Check A converts the FA-002 observation to `datetime` for comparison. The `float` comparison in Check C is exact (no precision loss), but the `datetime` comparison in Check A might have subtle precision differences if the conversion path differs.
- **why it matters**: In practice, both paths use `datetime.fromtimestamp()` with the same precision, so this is not a real issue. But the asymmetry between `float` in `_IdentitySnapshot` and `datetime` in Check A is a minor code clarity concern.
- **recommended fix**: No code change needed. The current approach is correct and the precision is consistent.

### m4. `hashlib.file_digest()` return type not asserted

- **severity**: minor
- **affected file**: `src/file_agent/hasher/hasher.py:204`
- **concrete problem**: `digest = hashlib.file_digest(handle, "sha256")` — the return type is `hashlib._Hash`, but this is not explicitly asserted. If `hashlib.file_digest` were to return `None` on some edge case, `digest.hexdigest()` would fail with `AttributeError` (caught by the outer `except Exception` as `INTERNAL_ERROR`).
- **why it matters**: This is an extreme edge case — `hashlib.file_digest` always returns a hash object for valid algorithms. The outer `try/except` provides a safety net.
- **recommended fix**: No code change needed. The outer `try/except Exception` catches `AttributeError`. Document the assumption.

### m5. `bytes_read` is auxiliary and may be 0 for empty files

- **severity**: minor
- **affected file**: `src/file_agent/hasher/hasher.py:213-215`
- **concrete problem**: `bytes_read = handle.tell()` is used in the `MODIFIED_DURING_HASH` error message. For empty files, `handle.tell()` returns 0. The error message `f"file identity/metadata changed during read (bytes_read=0)"` is technically correct but could be confusing — a change detected for an empty file would show `bytes_read=0`.
- **why it matters**: This is a minor diagnostic clarity issue, not a correctness issue.
- **recommended fix**: No code change needed. The error message is still informative.

## Test gaps

### T1. No test for `resolve_for_containment()` with a path containing `..` segments

- **severity**: medium (test gap)
- **concrete problem**: No test constructs a `DiscoveredFile` with a path like `C:\sandbox\sub\..\file.txt` and verifies that the hasher normalizes it and hashes `C:\sandbox\file.txt`.
- **recommended test**: Add a test that creates `sandbox/sub/file.txt`, constructs a `DiscoveredFile` with path `sandbox/sub/../file.txt`, and verifies the hasher produces a valid hash.

### T2. No test for the hasher when the file is replaced with a different file having identical metadata

- **severity**: low (test gap)
- **concrete problem**: No test creates two files with identical size and timestamps, then swaps one for the other between scanning and hashing.
- **recommended test**: This is an extremely rare edge case. Document that the hasher relies on metadata comparison, not inode comparison, with the FA-002 observation.

### T3. No test for the hasher when the file is truncated to zero during the read

- **severity**: low (test gap)
- **conmediate problem**: The `test_modified_during_hash_detected` test simulates a size increase, but not a size decrease (truncation to zero).
- **recommended test**: Add a monkeypatch test that simulates truncation during the read (modify `os.fstat` to return `st_size=0` for the second call).

### T4. No test for the hasher when `os.fstat()` fails after opening

- **severity**: low (test gap)
- **concrete problem**: No test simulates `os.fstat()` failing on an open file handle.
- **recommended test**: Add a monkeypatch test that makes `os.fstat()` raise `OSError` after the file is opened.

### T5. 1 symlink test skipped due to privilege requirements

- **severity**: low (test gap)
- **concrete problem**: `test_file_replaced_by_symlink_rejected_without_opening` is skipped when symlink creation fails.
- **recommended test**: Add a junction equivalent that tests the same property (file replaced by junction before open).

### T6. No test for the hasher's behavior when the file is a named pipe or socket

- **severity**: low (test gap)
- **concrete problem**: No test creates a named pipe or Unix domain socket inside the sandbox and verifies the hasher rejects it (not a regular file).
- **recommended test**: Add a test that creates a named pipe (Windows: `\\.\pipe\test_pipe`) and verifies the hasher returns `UNSUPPORTED_ENTRY_TYPE`. Skip on platforms where pipe creation is not available.

## Architectural observations

These are design decisions that should be documented and deferred to later tickets, not resolved in FA-003.

### A1. Path-based vs. handle-based identity verification

The hasher uses path-based containment and identity checking, not handle-based. This is a documented limitation: the gap between the pre-open reference check and `open()` cannot be prevented, only detected after the fact via `st_dev/st_ino` comparison. Closing this fully would require Win32 handle-based traversal (`CreateFile` with `FILE_FLAG_OPEN_REPARSE_POINT`), which is explicitly out of scope. The hasher's three-checkpoint identity chain (pre-open, post-open, post-read) provides the best possible detection within the path-based model.

### A2. No exclusive lock during hashing

The hasher doesn't take an exclusive lock on the file during hashing. This is a deliberate design choice — hashing stays a passive, non-disruptive reader. In-place content modification during the read is detected (via Check C), never prevented. This is the correct trade-off for a safety-focused system that should never modify the filesystem.

### A3. `DiscoveredFile` doesn't store st_dev/st_ino

The `DiscoveredFile` model stores metadata (size, timestamps) but not identity (st_dev/st_ino). This means the hasher can't compare identity with the FA-002 observation — only metadata. This is a deliberate design choice: the scanner's observation is a "point-in-time snapshot" of metadata, not a persistent identity token. The hasher's identity chain (checkpoint1→checkpoint2→checkpoint3) provides sufficient protection within the documented threat model.

### A4. Hash computation is separate from classification

Hashing (FA-003) is a separate stage from scanning (FA-002) and classification (FA-004+). This allows each stage to focus on its own concerns: scanning discovers files, hashing computes SHA-256, classification categorizes files. The `DiscoveredFile.with_sha256()` method produces an updated snapshot without mutating the original, preserving the immutable snapshot pattern from FA-001.

## Verdict

**APPROVE**

The hasher's containment enforcement is sound — `resolve_for_containment()` is called before any file is inspected, and the resolved path is checked against the sandbox root. The identity verification chain (three checkpoints: pre-open stat, post-open fstat, post-read fstat) correctly detects file replacement, symlink/junction injection, and mid-read modification. The streaming hash computation uses `hashlib.file_digest()` with proper chunked reading. Error types are semantically distinct and correctly classified (CRITICAL for containment violations and internal bugs, WARNING for environmental conditions). The read-only guarantee is upheld (verified by AST guardrail). The implementation is well-tested (19 passed, 1 skipped). No critical or major issues found.
