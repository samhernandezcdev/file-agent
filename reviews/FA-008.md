# FA-008 — Adversarial Transaction Engine Review

## Verdict: APPROVE

The transaction engine is the first filesystem mutation boundary in this codebase. The design is sound: prepare()/commit() split, one-shot capability tokens, default-deny preconditions, sole mutation primitive via `Path.rename()`, and two layers of AST guardrails (repo-wide and package-local) enforcing the architectural invariant. The implementation is clean, the test suite is thorough, and the safety properties are demonstrable. Issues below are minor.

## Minor

### m1. `_PreparedMove` is importable but not type-safe against cross-engine use

`_PreparedMove` is a frozen dataclass with a single `_token: UUID` field. It is importable via `file_agent.transaction_engine.engine._PreparedMove` (the test `test_prepared_move_bypass.py` does exactly this). The engine's `commit()` relies on the token being in `self._pending` -- a dict keyed by UUID. A caller who constructs `_PreparedMove(_token=uuid4())` and passes it to a different engine instance gets `InvalidPreparedMoveError`, which is correct. But the same UUID collision (astronomically unlikely but logically possible) across two different engines could theoretically allow a capability from engine A to be consumed by engine B if both share the same `_pending` registry. In practice this is impossible because each `TransactionEngine` instance has its own `_pending` dict, and UUID4 collision probability is negligible.

**Affected code**: `engine.py:51-64` (_PreparedMove definition), `engine.py:139` (commit lookup)

**Why it matters**: Cosmetic -- the design is correct by construction. The capability is one-shot (`.pop()`), per-instance, and opaque. No type-system enforcement could improve this without adding unnecessary complexity.

### m2. No test for `Path.rename()` raising a non-OSError exception

`engine.py:149` catches `OSError` from `move()` and returns `TransactionStatus.FAILED`. If `Path.rename()` raised a different exception (e.g., `ValueError`, which it doesn't), that exception would propagate unhandled. In CPython, `Path.rename()` raises `OSError` on failure -- this is a CPython implementation guarantee, not a Python language specification.

**Affected code**: `engine.py:147-158` (try/except in commit)

**Why it matters**: Very low -- `Path.rename()` is documented to raise `OSError` on failure. A future alternative Python implementation could theoretically violate this, but no such implementation exists. The current behavior is correct for CPython.

### m3. `check_destination_parent_exists` uses `is_dir()` which follows symlinks

`preconditions.py:109` calls `request.destination_path.parent.is_dir()`. If the parent directory is a symlink to a directory, `is_dir()` returns `True` -- which is the desired behavior (the parent exists and is a directory). But this means a symlinked parent that resolves outside the sandbox would pass this check. This is caught earlier by `check_destination_containment` (which resolves and checks `is_relative_to`), so the ordering matters.

**Affected code**: `preconditions.py:109` (destination parent check)

**Why it matters**: Low -- the precondition ordering ensures containment is verified before the parent check. The parent check is a mechanical "does the directory exist" check, not a containment check. The design relies on ordering, and the ordering is correct.

### m4. `check_destination_collision` does not check for FIFO/device files

`preconditions.py:114-122` checks `destination.exists()`, `destination.is_symlink()`, and `os.path.isjunction(destination)`. It does not check for FIFOs, block devices, or character devices. On Windows, these file types are extremely rare (named pipes are FIFOs but are typically created by other processes, not by the user). If a FIFO existed at the destination path, `destination.exists()` would return `True` (FIFOs are "files" on POSIX), but on Windows named pipes may behave differently.

**Affected code**: `preconditions.py:114-122`

**Why it matters**: Very low -- the `exists()` check covers regular files, directories, and symlinks. On Windows, FIFOs and device files are not common user-created artifacts. The current checks are sufficient for the intended use case.

### m5. No test for `transaction_result_event` when `completed_at` is None

`engine.py:265-267` has a fallback: `result.completed_at if result.completed_at is not None else result.evaluated_at`. This fallback is unreachable in practice because `TransactionResult` domain invariants enforce that `SUCCEEDED` and `FAILED` both require `completed_at`. For `REJECTED`, `completed_at` is `None`, but `REJECTED` results never have `started_at`/`completed_at` set. The fallback is defensive code that can never be exercised.

**Affected code**: `engine.py:265-267`

**Why it matters**: Cosmetic -- the fallback is correct but unreachable. A test proving it's unreachable would be documentary.

### m6. `verify_source_identity` constructs a `DiscoveredFile` with `created_at`/`modified_at` but `FileHasher.hash_file` may use different timestamp semantics

`preconditions.py:138-143` constructs a `DiscoveredFile` with `created_at=request.expected_created_at` and `modified_at=request.expected_modified_at`. `FileHasher.hash_file` uses these for identity verification (pre-open metadata match). The `DiscoveredFile` model's `created_at` and `modified_at` fields are timezone-aware datetime objects, and `TransactionRequest`'s `expected_*` fields are also timezone-aware (enforced by `normalize_to_utc`). The types match.

**Affected code**: `preconditions.py:138-143`

**Why it matters**: Cosmetic -- the types are correct and the semantic contract is maintained.

### m7. `PHYSICAL_DIRECTORY_FOR_DESTINATION_CATEGORY` does not cover `DestinationCategory.OTHER`

`rules.py:22-30` maps all seven `DestinationCategory` members. `OTHER` is not in the mapping (it's `DestinationCategory` but the physical directories only cover the seven that have physical counterparts). Wait -- actually checking the enum, `DestinationCategory` has: DOCUMENTS, IMAGES, AUDIO, VIDEO, ARCHIVES, CODE, EXECUTABLES. There is no `OTHER` in `DestinationCategory`. The mapping covers all members.

**Affected code**: `rules.py:22-30`

**Why it matters**: N/A -- after verification, this is not an issue.

### m8. `has_unsafe_reparse_ancestor` does not check the path itself for `is_unsafe_reparse_point`

`_paths.py:37-55` first calls `is_unsafe_reparse_point(path)` on line 48, which checks if `path` itself is a symlink/junction. Then it iterates `path.parents`. The `path` parameter is typically `request.destination_path.parent` (from `preconditions.py:101`), so it's checking the parent directory chain. This is correct.

**Affected code**: `_paths.py:48-54`

**Why it matters**: N/A -- after verification, the logic is correct.

## Architectural observations

1. **Mutation boundary is correctly isolated.** `operations.py` contains exactly one function (`move`) that calls exactly one mutation primitive (`Path.rename()`). Two AST guardrails enforce this: `test_mutation_boundary.py` (repo-wide, checks all `src/file_agent/` except `operations.py` and `persistence/`) and `test_mutation_boundary_within_package.py` (package-local, checks all `transaction_engine/*.py` except `operations.py`). Both tests verify the approved file actually contains the mutation call (vacuous-guard prevention).

2. **`Path.rename()` is the correct primitive.** `os.replace()` overwrites (violates "must never overwrite"). `shutil.move()` falls back to copy+delete (not atomic, can leave partial destination). `Path.rename()` raises `OSError` if the destination exists on Windows -- a genuine OS-level backstop. The `check_destination_collision` precondition provides an additional application-level check.

3. **prepare()/commit() split is sound.** `prepare()` never mutates the filesystem. It evaluates preconditions, mints a token, and returns a `_PreparedMove` capability. `commit()` is the only moment the filesystem changes. The split allows the caller to persist a `TRANSACTION_REQUESTED` checkpoint between the two calls (the crash-window seam). The test `test_crash_after_commit_before_terminal_persist_leaves_orphaned_requested` proves the resulting orphaned-event signature.

4. **One-shot capability consumption is correct.** `_PreparedMove` is a frozen dataclass with an opaque `_token: UUID`. `commit()` uses `self._pending.pop(token)` -- one-shot consumption. A forged token, a token from a different engine instance, or an already-consumed token all raise `InvalidPreparedMoveError`. The test `test_commit_ignores_caller_controlled_state_and_uses_only_the_registry` proves that even a copied token (same UUID, different object identity) works -- commit is driven entirely by the registry lookup, not by the object's identity.

5. **Precondition ordering is correct.** The chain is: authorization linkage → policy is AUTO → destination category matches policy → source not destination → basename preserved → destination category physical path → destination containment → destination parent exists → destination collision → source identity verification. This ordering ensures cheap in-memory checks run first, filesystem-touching checks (collision, identity) run last. The `verify_source_identity` call (which re-reads and re-hashes the source file) is intentionally the final step.

6. **Source identity verification reuses FA-003's chain.** `verify_source_identity` constructs a synthetic `DiscoveredFile` from the request's expected metadata and calls `FileHasher.hash_file()`. This transitively proves source-side containment and reparse safety (FileHasher independently re-validates both). No separate source-side check is duplicated. The test `test_source_outside_sandbox_is_rejected` proves this works.

7. **REJECTED vs FAILED vs SUCCEEDED semantics are correct.** REJECTED means zero filesystem risk (precondition failed before any OS call). FAILED means every precondition passed, the OS mutation call was actually issued, and the OS returned an error. SUCCEEDED means the mutation call returned successfully. The `TransactionResult` domain model enforces cross-field invariants (REJECTED requires rejection_code, no failure_reason; FAILED requires failure_reason; SUCCEEDED requires verified_sha256; started_at <= completed_at).

8. **Audit events are complete.** `transaction_requested_event()` captures the full request lineage. `transaction_result_event()` captures the full result lineage including status, rejection_code, failure_reason, verified_sha256, timestamps, and transaction_engine_id. Both are pure mapping functions (no persistence dependency). The persistence integration test proves the full REQUESTED → terminal event flow.

9. **Destination collision check is conservative.** `check_destination_collision` checks `destination.exists()`, `destination.is_symlink()`, and `os.path.isjunction(destination)`. The symlink check is necessary because `Path.exists()` follows symlinks -- a dangling symlink would return `False` from `exists()` but `True` from `is_symlink()`. The junction check uses `os.path.isjunction()` (not `Path.is_junction()`, which doesn't exist in Python's stdlib). Both checks are correct.

10. **Reparse point safety is conservative.** `has_unsafe_reparse_ancestor` checks the path itself and every ancestor up to (but not including) the boundary. This mirrors the scanner's conservative "never follow a reparse point, even one that would resolve inside the sandbox" policy. The junction tests prove both out-of-bounds and in-bounds junctions are rejected.

11. **No naming transformation.** The engine never modifies the filename. `check_basename_preserved` ensures `source_path.name == destination_path.name`. The `TransactionRequest` domain model allows the caller to set any `destination_path`, but the engine rejects basename mismatches.

12. **No LLM integration.** The transaction engine has no LLM dependency, no classifier dependency, no policy evaluation logic. It mechanically executes an already-authorized decision. AUTO means "eligible for execution," not "executed." The engine still requires an explicit `commit()` call.

13. **`TRANSACTION_ENGINE_ID = "v1"` is a stable provenance identifier.** Unlike the classifier/proposal-engine/policy-engine (which have interpretive rule tables), the transaction engine's preconditions are fixed mechanical checks. The ID is bumped only if the precondition set or mutation primitive changes. The `PHYSICAL_DIRECTORY_FOR_DESTINATION_CATEGORY` mapping is defined independently of FA-006's proposal mapping (same "defined independently, may intentionally diverge" precedent).

14. **Windows assumptions are correct.** `Path.rename()` raises `OSError` on Windows if the destination exists. `os.path.isjunction()` is Windows-specific (returns `False` on other platforms). `subprocess.run(["cmd", "/c", "mklink", "/J", ...])` is used in tests to create junctions. The 9 skipped tests are for symlink privilege requirements (symlinks on Windows require elevated privileges).

## Summary

FA-008 implements the first filesystem mutation boundary in the codebase. The prepare()/commit() split, one-shot capability tokens, and AST guardrails form a sound defense-in-depth design. The precondition chain is correctly ordered (cheap in-memory checks first, filesystem-touching checks last). Source identity verification reuses FA-003's entire three-checkpoint chain. Destination collision and reparse safety are conservatively checked. The sole mutation primitive (`Path.rename()`) is the correct choice for same-volume moves on Windows. The test suite covers all rejection paths, bypass attacks, crash window semantics, persistence integration, and both AST guardrails. The minor issues -- non-OSError exception handling, unreachable fallback code, FIFO collision -- are theoretical edge cases that don't affect correctness or safety for the intended use case.
