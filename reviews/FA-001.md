# FA-001 — Adversarial Review

Reviewed: `src/file_agent/domain/` (5 modules), `tests/domain/` (7 test files), `docs/SAFETY.md`.

---

## Critical

No issues blocking merge. The domain layer is cleanly separated, correctly frozen, and free of filesystem I/O. The core safety invariants from SAFETY.md are structurally upheld at this layer.

---

## Major

### M1. Mutable nested containers undermine `frozen=True`

- **severity**: major
- **affected file**: `src/file_agent/domain/events.py:46`
- **concrete problem**: `DomainEvent.payload` is a plain `dict[str, Any]`. Pydantic's `frozen=True` prevents attribute reassignment (`event.payload = {}` raises), but does **not** prevent item mutation (`event.payload["key"] = "value"` succeeds silently). The same applies to `FileProposal.reasons` (a `list[str]`).
- **why it matters**: The frozen contract is the backbone of the immutability assumption shared by all domain models. Silent container mutation means a caller can alter event payloads after construction, corrupting the audit trail and violating the intent of SAFETY.md ("confidence != permission" — a frozen proposal should be tamper-proof). Any downstream code that trusts frozen semantics will have a false sense of safety.
- **recommended change**: Wrap mutable defaults with `types.MappingProxyType` (dict) and `tuple` (list) in a custom `__init__` or via Pydantic's `model_validator(mode='wrap')`, or use `pydantic-core`'s `SchemaValidationEventHandler` to deep-freeze on construction. Document the choice. At minimum, add a test proving the limitation exists so future contributors don't assume full immutability.

### M2. `ScanRun.evolve()` can change identity and immutable fields

- **severity**: major
- **affected file**: `src/file_agent/domain/scan.py:63-71`
- **concrete problem**: `evolve(**changes)` merges arbitrary changes into the model dump. A caller can pass `id=uuid4()` to reassign the entity's identity, or `root_path=new_path` to change the scan's root. The existing test (`test_evolve_valid_transition`) asserts `completed.id == scan.id`, but this is a convention, not enforcement.
- **why it matters**: The identity of an entity must be immutable across its lifecycle. If `evolve()` can change `id`, the snapshot sequence loses referential integrity — events, proposals, and foreign keys referencing the old `id` become orphaned silently. Changing `root_path` after creation contradicts the model's purpose as an immutable record of a scan.
- **recommended change**: In `evolve()`, reject changes to `id` and `root_path` explicitly: `rejected = changes.keys() & {"id", "root_path"}; if rejected: raise ValueError(...)`. Consider a stricter `evolve()` that only accepts lifecycle fields (`status`, `completed_at`, `files_discovered`).

### M3. SHA-256 lifecycle creates an identity paradox

- **severity**: major
- **affected file**: `src/file_agent/domain/file.py:27`
- **concrete problem**: `DiscoveredFile.sha256` is optional, designed so the entity can exist before hashing. But `DiscoveredFile` is frozen — there is no mechanism to set the hash after construction. To attach a hash, you must create a new `DiscoveredFile` with a new `UUID`, breaking the identity chain. The `FILE_HASHED` event implies the same entity now has a hash, but the model makes this impossible without creating a new identity.
- **why it matters**: This is a fundamental lifecycle modeling problem. Either the hash should be set at construction time (making `FILE_DISCOVERED` and `FILE_HASHED` redundant as separate events), or the domain needs a way to produce an updated snapshot with the same identity (similar to `ScanRun.evolve()`). As-is, there's no clean way to represent "this file, which was discovered earlier, now has a known hash."
- **recommended change**: Option A: Add an `evolve()` or `with_hash()` method on `DiscoveredFile` that produces a new instance with the same `id` but `sha256` set. Option B: Drop the `FILE_HASHED` event and have `FILE_DISCOVERED` carry the hash when available. Option C: Accept the limitation and document it — but this needs a deliberate design decision, not an oversight. This is the most important design question in FA-001.

### M4. `DiscoveredFile` field consistency not enforced

- **severity**: major
- **affected file**: `src/file_agent/domain/file.py:12-41`
- **concrete problem**: `path`, `filename`, and `extension` are three independent fields with no invariant enforcing consistency. You can construct a `DiscoveredFile` where `path=Path("/docs/report.pdf")`, `filename="data.csv"`, `extension="txt"` — all three disagree. The `extension` validator only normalizes case and strips the leading dot; it does not verify it matches `filename` or `path`.
- **why it matters**: These fields are meant to describe the same physical file. Inconsistent values will silently propagate to downstream consumers (the classifier, the proposal generator, the UI). A file reported as `.txt` with an `.pdf` path will produce confusing proposals.
- **recommended change**: Add a `model_validator(mode='after')` that verifies: (a) `path.name == filename`, (b) `path.suffix.lower().lstrip(".") == extension`. Alternatively, derive `filename` and `extension` from `path` and make them computed/read-only.

## Minor

### m1. `DomainEvent` has no typed payloads per event type

- **severity**: minor
- **affected file**: `src/file_agent/domain/events.py:46`
- **concrete problem**: `payload` is `dict[str, Any]` with no per-event-type schema. `FILE_HASHED` could be created without a `sha256` key; `PROPOSAL_CREATED` could omit `file_id`. The only validation is JSON-serializability.
- **why it matters**: This pushes schema validation to every consumer. A `FILE_HASHED` event without a hash is meaningless but constructible. Typed payloads (via discriminated unions or per-event models) would catch these at construction time.
- **recommended change**: Out of scope for FA-001 (would require restructuring EventType into a class hierarchy or adding payload schema registry). Document this as a known limitation.

### m2. `test_no_filesystem_mutations.py` has significant gaps

- **severity**: minor
- **affected file**: `tests/domain/test_no_filesystem_mutations.py:9-18`
- **concrete problem**: The forbidden token list misses `Path.mkdir`, `Path.write_text`, `Path.write_bytes`, `Path.open` (write mode), `os.mkdir`, `os.makedirs`, `os.symlink`, `os.link`, `os.chmod`, `os.chown`. It also doesn't catch `importlib.import_module('os').remove` or `from os import remove`. The `.replace(` token is overly broad — it matches string `.replace()` too, though this hasn't caused false positives yet.
- **why it matters**: The test provides a false sense of security. A contributor could add `Path("foo").write_text("...")` and the test would pass. The guardrail is a convention, not a guarantee.
- **recommended change**: Expand the token list. Consider using `ast` module to parse the source and check for dangerous imports/calls, which is more robust than string matching.

### m3. No serialization round-trip tests for models with `Path` fields

- **severity**: minor
- **affected file**: `tests/domain/test_file.py`, `tests/domain/test_proposal.py`
- **concrete problem**: `test_events.py` tests `model_dump_json()` / `model_validate_json()` round-trip, but `DiscoveredFile` and `FileProposal` (which contain `Path` fields) have no equivalent tests. `Path` serialization to/from JSON is not verified.
- **why it matters**: If Pydantic's `Path` serialization changes or has edge cases (e.g., UNC paths on Windows), the round-trip would silently break.
- **recommended change**: Add round-trip tests for `DiscoveredFile` and `FileProposal` covering Windows paths, UNC paths, and paths with special characters.

### m4. `FileProposal` allows `confidence=1.0` with no actionable output

- **severity**: minor
- **affected file**: `src/file_agent/domain/proposal.py:39-43`
- **concrete problem**: A proposal with `confidence=1.0`, `proposed_name=None`, `proposed_destination=None`, and `reasons=["classified"]` is valid. A 100% confident proposal that proposes nothing is semantically contradictory.
- **why it matters**: Downstream code (the TransactionEngine) will need to handle this case. A high-confidence proposal with no actionable destination is an invalid state that the model should reject.
- **recommended change**: Add a model validator: if `confidence >= some_threshold` (e.g., 0.5), require at least one of `proposed_name` or `proposed_destination`. Or document the convention that confidence never implies actionability (SAFETY.md rule 6).

### m5. `modified_at >= created_at` not enforced on `DiscoveredFile`

- **severity**: minor
- **affected file**: `src/file_agent/domain/file.py`
- **concrete problem**: A `DiscoveredFile` where `modified_at` is before `created_at` is valid. While this could be legitimate (e.g., file copied preserving original timestamps), it's more often an error.
- **why it matters**: Downstream code may assume `modified_at >= created_at` for staleness checks or conflict resolution.
- **recommended change**: Add a model validator or document the decision. If the intent is to preserve original timestamps without judgment, note it explicitly.

### m6. `reasons` field has `min_length=1` but no max length

- **severity**: minor
- **affected file**: `src/file_agent/domain/proposal.py:43`
- **concrete problem**: `reasons` requires at least one string, but has no upper bound. A classification could produce hundreds of reasons, bloating the model.
- **recommended change**: Add `max_length` constraint or document the expected range.

## Test gaps

### T1. No test for mutable container mutation on frozen models

- **severity**: high (test gap)
- **concrete problem**: `test_frozen_mutation_raises` only tests attribute reassignment. It does not test `event.payload["key"] = "value"` or `proposal.reasons.append("x")`, which succeed silently.
- **recommended test**: Add tests proving that `DomainEvent.payload` and `FileProposal.reasons` are mutable despite `frozen=True`, and document whether this is accepted or needs fixing.

### T2. No test for `ScanRun.evolve()` changing `id`

- **severity**: high (test gap)
- **concrete problem**: `test_evolve_valid_transition` asserts `completed.id == scan.id`, but no test verifies that `scan.evolve(id=uuid4())` is rejected. If M2 is fixed, this test becomes a regression guard.
- **recommended test**: Add a test that calls `scan.evolve(id=uuid4())` and asserts `ValidationError` (once M2 is implemented).

### T3. No Windows path tests

- **severity**: medium (test gap)
- **concrete problem**: No tests for UNC paths (`\\server\share\file.txt`), extended-length paths (`\\?\C:\long\path`), drive-relative paths (`C:foo.txt`), or mixed-separator paths (`C:/foo/bar`). The `ensure_absolute_path` validator uses `Path.is_absolute()`, which behaves differently across platforms.
- **recommended test**: Add parametrized tests for Windows path edge cases, or document that these are only relevant on Windows CI.

### T4. No DST or unusual UTC offset datetime tests

- **severity**: medium (test gap)
- **concrete problem**: Tests only cover `timezone(timedelta(hours=2))`. No tests for negative UTC offsets, UTC+12 (dateline edge), DST transitions, or leap seconds.
- **recommended test**: Add parametrized tests for `timezone(timedelta(hours=-12))`, `timezone(timedelta(hours=13))`, and DST-boundary datetimes.

### T5. No test for `FileProposal` high confidence without destination

- **severity**: medium (test gap)
- **concrete problem**: No test constructs a `FileProposal` with `confidence=1.0` and `proposed_name=None, proposed_destination=None` to verify whether the model accepts or rejects it.
- **recommended test**: Add this test to clarify the intended behavior.

### T6. No test for `DiscoveredFile` field consistency

- **severity**: medium (test gap)
- **concrete problem**: No test constructs a `DiscoveredFile` where `path.name != filename` or `extension` doesn't match `path.suffix`.
- **recommended test**: Add a test verifying that inconsistent field combinations are rejected (once M4 is fixed).

## Architectural observations

These are design decisions that should be documented and deferred to later tickets, not resolved in FA-001.

### A1. Sandbox enforcement is outside the domain layer

SAFETY.md rule 3 ("only read inside sandbox/") is not enforced at the domain model level. The domain accepts any absolute path. Sandbox enforcement belongs in the scanning layer (FA-002+). This is the correct separation of concerns, but should be documented in the domain layer's docstring.

### A2. Flat `DomainEvent` model is a pragmatic trade-off

The single-model-per-event approach is simpler than a discriminated union hierarchy, but it sacrifices type safety on payloads. This is acceptable for FA-001's scope (audit record, not event sourcing). Typed event variants should be an FA-002+ concern when event consumers need schema guarantees.

### A3. TransactionEngine and reversibility are later milestones

SAFETY.md rules 4 and 7 (TransactionEngine, audit/revert) are explicitly deferred. The domain layer provides the data model; the execution layer is a separate milestone. No action needed in FA-001.

### A4. Persistence strategy affects identity assumptions

SQLite persistence (likely FA-003+) will need to handle `UUID` primary keys, `Path` serialization, and `datetime` storage. The current Pydantic models are compatible, but the `evolve()` pattern and the SHA-256 lifecycle (M3) will need resolution before persistence is added.

---

## Verdict

**REQUEST CHANGES**

The domain layer is well-structured and correctly separated from I/O. However, M1 (mutable containers in frozen models) and M3 (SHA-256 lifecycle paradox) represent design inconsistencies that will propagate downstream if not addressed. M2 (evolve() identity mutation) and M4 (field consistency) are correctness issues that should be caught at the model level. Recommend resolving M1–M4 before merging, or explicitly documenting them as accepted limitations with linked follow-up tickets.
