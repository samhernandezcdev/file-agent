# FA-004 — Persistence Layer Review

## Verdict: APPROVE

The persistence layer is well-architected. Transaction boundaries are clean, the error taxonomy is complete and correctly isolated, event deduplication handles the race condition properly, and all type round-trips work. The issues below are real but non-blocking — they don't undermine correctness or safety.

## Critical

No critical issues found.

## Major

### M1. Assertion in `insert_event` masks a production bug

`repositories.py:93-95`:

```python
existing = session.get(DomainEventRow, row.id, populate_existing=True)
assert existing is not None, (
    "on_conflict_do_nothing with rowcount=0 implies a row exists"
)
```

If the row genuinely doesn't exist after a `rowcount=0` result (which shouldn't happen with correct SQLite behavior, but could with a misconfigured or hypothetical non-SQLite backend), this assertion silently passes in production (Python `-O`) or crashes with an unhelpful `AssertionError` instead of raising `IntegrityConstraintError`. Replace with an explicit guard:

```python
if existing is None:
    raise IntegrityConstraintError(
        f"event id={row.id} vanished between INSERT and SELECT"
    )
```

**Severity justification**: Major because the invariant *should* hold under SQLite, and the fix is trivial. It doesn't affect correctness today.

### M2. Tests use `Base.metadata.create_all` instead of Alembic migrations

`conftest.py:39`:

```python
Base.metadata.create_all(engine)
```

This creates the schema directly from ORM metadata, bypassing Alembic. This means:
- Tests never exercise the actual migration path (`0001_initial_schema.py`)
- A migration that drops a column or changes a constraint won't break tests, because `create_all` creates the final schema directly
- `test_alembic_head_matches_orm_metadata` partially covers this gap, but only for `compare_metadata` — not for the data-integrity implications of a migration's `upgrade()` function

The `test_migrations.py` tests use `command.upgrade(cfg, "head")`, which is correct. But the main test suite's `conftest.py` should also use Alembic so that everyday persistence tests exercise the real migration path.

**Severity justification**: Major because it weakens the migration test coverage without eliminating it.

## Minor

### m1. `record_scan` partial-insert on conflicting event

If `record_scan` processes events in a loop and the third event conflicts, the first two events are already flushed (but not committed). The `IntegrityError` handler triggers a rollback via `session.begin()`'s context manager, so nothing persists — correct behavior. But the error message "event id=... already exists with different content" is raised as `IntegrityConstraintError`, not `IntegrityError`, so it flows through the application-level raise on line 57-59, not the `except IntegrityError` on line 60. This is intentional and correct, but worth a code comment explaining the two distinct raise sites for the same error type.

### m2. Hardcoded `_REPO_ROOT` path in `engine.py`

`engine.py:23`:

```python
_REPO_ROOT = Path(__file__).resolve().parents[3]
```

This computes the repo root relative to the source file's location. It works for the current project layout but is fragile if the directory structure changes. Consider accepting `alembic_ini_path` as a required parameter rather than computing a default from a relative path (the `assert_schema_up_to_date` function already accepts it as an optional parameter, but `DEFAULT_ALEMBIC_INI` is still computed at module level).

### m3. AST guardrail doesn't catch all mutation patterns

`test_app_data_boundary.py` checks for `os.remove`, `shutil.rmtree`, `.write_text`, etc. but doesn't check for `builtins.open(..., 'w')` or `pathlib.Path.open(..., 'w')`. A persistence file could theoretically call `open(path, 'w')` without triggering the guardrail. The current code doesn't do this, but the guardrail is incomplete.

### m4. No test for `list_discovered_files` and `list_events` as standalone queries

These methods are only tested indirectly (via `record_scan` then `get_discovered_file`, or via `record_event` then `list_events`). A dedicated test for `list_discovered_files` with multiple scans, or `list_events` with multiple entity types, would strengthen coverage.

### m5. No test for `record_scan` with zero events

`record_scan` is tested with one or two events, but never with `events=()` explicitly verified for event count. The `make_scan_result` fixture generates events for each file, but there's no test that verifies `record_scan` with an explicitly empty events tuple leaves zero events in the store (only `test_repeated_scans_of_same_path_do_not_overwrite_unrelated_observations` uses `events=()` indirectly, and it doesn't assert on event count).

### m6. `record_event` return value semantics could be clearer

`record_event` returns `True` if newly inserted, `False` if identical duplicate. The docstring says this correctly, but the method name `record_event` doesn't hint at a boolean return. A caller might ignore the return value and miss a conflict. This is a design-level observation, not a bug.

## Architectural observations

1. **Transaction boundaries are sound.** Every write method in `FileAgentStore` follows the same pattern: `session.begin()` context manager + repository calls + `except` translation + `finally session.close()`. The `with session.begin()` semantics guarantee rollback on any exception. The two-write atomicity in `record_hash_success` (update observation + insert event) is correctly wrapped in a single transaction.

2. **Event deduplication is race-free.** The INSERT-first algorithm (`on_conflict_do_nothing` then compare) in `insert_event` correctly handles the concurrent case. The test in `test_concurrent_duplicate_event_race_resolves_deterministically` proves this with a real `ThreadPoolExecutor`.

3. **Error taxonomy is clean and complete.** `errors.py` defines five error types, all subclassing `PersistenceError`. `store.py` is the only translation boundary — `repositories.py` never catches or translates. The `IntegrityConstraintError` vs `DatabaseUnavailableError` distinction is correct: application-level logic errors vs infrastructure errors.

4. **Type round-trips are faithful.** `GUIDText` preserves UUID identity, `UTCDateTimeText` enforces aware UTC datetimes, and `DomainEvent.payload` is reconstructed as `MappingProxyType` (frozen). The `MappingError` exception for naive datetimes and bad enum values is correct.

5. **App-data boundary is enforced.** The AST guardrail in `test_app_data_boundary.py` proves that the only filesystem mutation call in the persistence package is `config.root.mkdir()` in `engine.py`. The integration test proves a full persistence run doesn't touch a sandbox tree.

6. **Schema management is correct.** `assert_schema_up_to_date` compares the Alembic head revision against the database's current revision without running migrations itself. The Alembic `env.py` supports an `x db_path` override for testing convenience, but the application itself always uses `AppPaths`.

7. **Re-hashing is correct.** `update_observation_hash` is unconditional — sha256 can change more than once. The `record_hash_success` method verifies the observation exists (rowcount > 0) and appends a new event each time, even for the same hash. This preserves the full event history.

---

## Summary

The persistence layer is production-quality. The two major issues (assertion-as-invariant, test bypass via `create_all`) are worth fixing but don't block the milestone. The minor issues are design observations and test coverage gaps. The architecture — transaction boundaries, error taxonomy, event deduplication, type round-trips, app-data containment — is sound.
