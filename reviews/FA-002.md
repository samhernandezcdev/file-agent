## Minor

### m1. `is_unc_path()` incorrectly rejects extended-length Windows paths

- **severity**: minor
- **affected file**: `src/file_agent/scanner/_paths.py:9-11`
- **concrete problem**: `is_unc_path()` checks `path.drive.startswith("\\\\")`. Extended-length paths (`\\?\C:\...`) have a drive that starts with `\\`, so they are rejected as UNC even though they are not UNC paths. UNC drives are `\\server\share`; extended-length drives are `\\?\...` or `\\?\UNC\server\share`.
- **why it matters**: A user with a deep directory structure exceeding MAX_PATH (260 chars) cannot use an extended-length sandbox root. The rejection is conservative (safe) but incorrect.
- **recommended fix**: Check for `drive.startswith("\\\\?\\")` or `drive.startswith("\\?\\")` explicitly and allow it, or use `path.drive.startswith("\\\\") and not path.drive.startswith("\\\\?\\")`.

### m2. Mount points silently rejected as sandbox roots

- **severity**: minor
- **affected file**: `src/file_agent/scanner/_paths.py:14-31`
- **concrete problem**: `is_reparse_point()` catches `FILE_ATTRIBUTE_REPARSE_POINT`, which is set for NTFS mount points. `SandboxRoot.from_path()` rejects any reparse-point root, so a directory that is a volume mount point (e.g., `C:\Mount\Data` → `D:\`) is rejected.
- **why it matters**: Mount points are a legitimate way to organize directories on Windows. Rejecting them is conservative but may surprise users. During scanning, a directory that is a mount point inside the sandbox is also correctly skipped (logged as `UNSUPPORTED_REPARSE_POINT`), which is the right security behavior.
- **recommended fix**: Document this limitation, or add a specific check that distinguishes mount points from symlinks/junctions (mount points use `IO_REPARSE_TAG_MOUNT_POINT`).

### m3. `_handle_reference()` resolves the full symlink chain

- **severity**: minor
- **affected file**: `src/file_agent/scanner/scanner.py:203-239`, `src/file_agent/scanner/_paths.py:34-47`
- **concrete problem**: `resolve_reference_target()` calls `path.resolve(strict=False)`, which follows the entire symlink chain to the ultimate target. A deeply nested symlink chain (approaching Windows's ~63-level nesting limit) could cause noticeable latency.
- **why it matters**: This is correct for containment checking (the final target is what matters), but a crafted chain of 50+ symlinks could slow the scan. This is a TOCTOU-adjacent concern and is acceptable under the documented threat model.
- **recommended fix**: No code change needed. Document that deeply nested symlink chains may cause latency.

### m4. `_walk_subdirectory()` materializes the full directory listing

- **severity**: minor
- **affected file**: `src/file_agent/scanner/scanner.py:106-107`
- **concrete problem**: `entries = list(os.scandir(directory))` loads all directory entries into memory before processing. A directory with millions of entries would consume significant memory.
- **why it matters**: This is a correct design choice (ensures listing is complete before processing), but could be a memory concern for extremely large directories. The trade-off is correct for the typical sandbox use case.
- **recommended fix**: No code change needed for FA-002. If memory becomes an issue, consider streaming with `for entry in os.scandir(directory)` and handling errors per-entry.

### m5. `file_times_from_stat()` has no POSIX correctness guarantee

- **severity**: minor
- **affected file**: `src/file_agent/scanner/_paths.py:50-58`
- **concrete problem**: `st_ctime` is creation time on Windows but metadata-change time on POSIX. The docstring documents this, but the function name `file_times_from_stat` doesn't convey the platform assumption.
- **why it matters**: If the scanner is ever run on POSIX, `created_at` would actually be metadata-change time, which is semantically wrong. The current Windows-only scope makes this acceptable.
- **recommended fix**: Add a `platform = sys.platform` guard or rename to `file_times_from_stat_windows` to make the platform assumption explicit.

## Test gaps

### T1. 8 symlink tests skipped due to privilege requirements

- **severity**: high (test gap)
- **concrete problem**: Tests `test_file_symlink_escaping_sandbox`, `test_directory_symlink_escaping_sandbox`, `test_symlink_targeting_inside_sandbox_not_followed`, `test_broken_symlink_is_unresolvable_not_escape`, `test_no_events_for_skipped_entries`, `test_escape_attempt_still_completes`, `test_rejects_symlink_root`, and `test_directory_symlink_to_own_parent_does_not_loop` are all skipped when symlink creation fails.
- **why it matters**: These tests cover the core security property (escape detection). On CI environments without symlink privileges, the containment enforcement is only verified through junction tests (which use `mklink /J` and don't require privileges). Junction tests provide partial coverage, but symlink-specific behavior (e.g., file vs. directory symlinks, broken symlinks) is untested on those environments.
- **recommended test**: Add a CI configuration that enables Developer Mode or runs with elevated privileges to execute symlink tests. Alternatively, document that junction tests provide equivalent coverage for the containment property.

### T2. No test for extended-length Windows paths

- **severity**: medium (test gap)
- **concrete problem**: No test constructs a `SandboxRoot` with an extended-length path (`\\?\C:\...`). This would reveal that `is_unc_path()` incorrectly rejects them.
- **recommended test**: Add a test `test_rejects_extended_length_path` or `test_accepts_extended_length_path` depending on the desired behavior.

### T3. No test for mount points as sandbox roots

- **severity**: low (test gap)
- **concrete problem**: No test constructs a `SandboxRoot` with a directory that is a mount point. This would verify the conservative rejection behavior.
- **recommended test**: Add a test documenting the mount point behavior (skip if mount point creation is not available in CI).

### T4. No test for symlink chains

- **severity**: low (test gap)
- **concrete problem**: No test creates a chain of multiple symlinks (e.g., `link1 -> link2 -> target`) and verifies that the scanner resolves the full chain and checks the final target.
- **recommended test**: Add a test with a 2-3 level symlink chain pointing inside and outside the sandbox.

### T5. No test for `_handle_reference()` when target is exactly the sandbox root

- **severity**: low (test gap)
- **concrete problem**: No test creates a symlink pointing exactly to the sandbox root path and verifies it's treated as internal (SYMLINK_NOT_FOLLOWED / INFO).
- **recommended test**: Add a test with `sandbox/link -> sandbox_root`.

### T6. No test for `ScanIssue.detected_at` timezone awareness

- **severity**: low (test gap)
- **concrete problem**: No test verifies that `ScanIssue.detected_at` is timezone-aware and in UTC.
- **recommended test**: Add an assertion in an existing test that checks `issue.detected_at.tzinfo is not None`.

## Architectural observations

These are design decisions that should be documented and deferred to later tickets, not resolved in FA-002.

### A1. Path-based vs. handle-based containment

The scanner uses path-based containment checking (`is_relative_to()`), not handle-based. This is a documented limitation: a TOCTOU race between classification and read could allow a symlink to be swapped. Closing this would require Win32 handle-based traversal (`CreateFile` with `FILE_FLAG_OPEN_REPARSE_POINT`), which is explicitly out of scope. The scanner's read-only constraint (metadata only, no file content reads) limits the blast radius of any TOCTOU race.

### A2. Internal symlinks/junctions are not walked

The scanner's policy is to not follow ANY symlinks or junctions, even those pointing inside the sandbox. This avoids infinite loops and duplicate discoveries, but means files reachable only through an internal symlink are not discovered. This is a deliberate policy choice — the real directory is already walked through the normal traversal. Document this as expected behavior.

### A3. ScanResult contains all data for downstream consumers

`ScanResult` bundles `scan_run`, `files`, `events`, and `issues` into a single immutable dataclass. Downstream consumers (hashing, classification, proposal generation) should use this as their input. This avoids coupling between the scanner and later stages. No action needed.

### A4. Hash computation belongs in FA-003

The scanner produces `DiscoveredFile` instances with `sha256=None`. Hash computation is a separate concern (FA-003) that should use `DiscoveredFile.with_sha256()` to produce updated snapshots. No action needed in FA-002.

## Verdict

**APPROVE**

The scanner's sandbox containment enforcement is solid under its documented threat model. All symlink/junction/reparse-point escapes are detected and blocked. The validation ordering in `SandboxRoot` is correct (reparse check before `resolve()`). Filesystem reads are strictly read-only (verified by AST guardrail). The `ScanRun` lifecycle is correct. Events are correctly emitted per discovered file. The implementation is well-tested (103 passed, 8 skipped due to platform limitations). No critical or major issues found. The minor findings are all non-blocking improvements or documentation gaps.
