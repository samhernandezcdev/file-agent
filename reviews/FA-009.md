# FA-009 — Adversarial Human Review Decision Review

## Verdict: APPROVE

The human review engine is clean, correctly scoped, and properly layered. HumanReviewEngine validates linkage/outcome rules and records a human's APPROVE/SKIP decision as an immutable domain fact. It performs zero filesystem I/O, is intentionally stateless, and does not integrate with TransactionEngine. The architectural boundary is sound. Issues below are minor.

## Minor

### m1. `HumanReviewDecision` can be constructed directly without engine validation

`HumanReviewDecision` is a Pydantic domain model with `frozen=True` and `extra="forbid"`, but nothing prevents a caller from constructing one directly via `HumanReviewDecision(...)` without passing through `HumanReviewEngine.record()`. The engine validates linkage (proposal_id/file_id/destination_category match), policy outcome (only REVIEW), and APPROVE-requires-destination. A manually-constructed `HumanReviewDecision` bypasses all these checks.

**Affected code**: `domain/human_review.py:39-86` (model definition)

**Why it matters**: This is the same layering precedent as `TransactionRequest` and `PolicyDecision` -- the domain model stays constructible for any combination a test needs; the engine decides what's actually allowed. The docstring on `HumanReviewDecision` explicitly states this: "structural linkage and outcome validity are engine concerns, not validated by this model itself." The trust boundary is the application/orchestration layer that calls `record_human_review()` and persists the resulting event. A manually-constructed `HumanReviewDecision` is not "trusted" unless the orchestration layer treats it as such -- and the production contract (one effective review per PolicyDecision) is enforced at that layer, not by the domain model.

**Mitigation**: No change needed. The current architecture establishes the engine/application layer as the trust boundary. If a future consumer accidentally treats a manually-constructed `HumanReviewDecision` as trusted authorization, that is an integration bug at the consumer, not a domain model defect. The domain model's job is to be immutable and self-contained; the engine's job is to validate what's allowed. This separation is deliberate and documented.

### m2. `human_review_recorded_event()` takes only the review, but the review carries all lineage

`engine.py:138-170` defines `human_review_recorded_event(review: HumanReviewDecision)` which takes only the review object. The payload is constructed entirely from the review's own fields (`policy_engine_id`, `proposal_engine_id`, etc.), so there is no second/third parameter through which unrelated objects could be paired. This is correct by construction. However, the function name `human_review_recorded_event` could be confused with a persistence call (it's a pure mapping function, not a persist function).

**Affected code**: `engine.py:138-170`

**Why it matters**: Cosmetic -- the docstring explicitly states "does not persist anything itself." The function is a pure mapping, same as `transaction_requested_event()` and `transaction_result_event()` in FA-008. The naming convention is consistent across the codebase.

### m3. `record_human_review()` convenience function creates a new engine per call

`engine.py:124-135` defines `record_human_review()` which instantiates `HumanReviewEngine()` and calls `.record()`. Since the engine is stateless (no `__init__` parameters other than an optional `clock`), this is fine. But it means a caller who needs a custom clock must use `HumanReviewEngine(clock=...)` directly, not the convenience function.

**Affected code**: `engine.py:124-135`

**Why it matters**: Low -- the convenience function is for the common case (default clock). Tests use `HumanReviewEngine(clock=fixed_clock)` directly when they need a fixed clock. The design is intentional: the convenience function is sugar, not the only path.

### m4. No test for `human_review_recorded_event` with `destination_category=None`

The persistence integration test (`test_persistence_integration.py`) creates a SKIP review for a proposal with `DestinationCategory.EXECUTABLES` (non-None). There is no persistence round-trip test for a SKIP review with `destination_category=None` (which is valid for UNKNOWN/OTHER proposals). The `human_review_recorded_event` function handles `None` correctly (line 159-162), but an explicit test would guard against future regressions.

**Affected code**: `engine.py:159-162` (None handling), `test_persistence_integration.py` (missing test)

**Why it matters**: Low -- the serialization logic is correct (the ternary `review.destination_category.value if review.destination_category is not None else None` is straightforward). A test would complete the coverage matrix.

### m5. `ReviewSource` enum has only one member (`USER`)

`domain/human_review.py:27-36` defines `ReviewSource` with a single member `USER`. The docstring explains: "Only USER today -- no AI/system approval source until a concrete need exists." This is the same single-member enum precedent as `TransactionOperation.MOVE`. The enum is kept for forward compatibility.

**Affected code**: `domain/human_review.py:27-36`

**Why it matters**: Cosmetic -- the design is intentional and documented. The enum exists so a future source can be added without changing every signature.

### m6. `note` field has `min_length=1` constraint but is `str | None`

`domain/human_review.py:78` defines `note: str | None = Field(default=None, min_length=1)`. This means a non-None note must have at least one character (empty string is rejected). The test `test_empty_note_rejected` confirms this. The constraint is correct.

**Affected code**: `domain/human_review.py:78`

**Why it matters**: N/A -- after verification, the constraint is correct.

## Architectural observations

1. **Authorization gating is correct and fail-closed.** The engine checks: (a) `policy_decision.proposal_id == proposal.id`, (b) `policy_decision.file_id == proposal.file_id`, (c) `policy_decision.destination_category == proposal.proposed_destination_category`, (d) `policy_decision.decision is not AUTO` (redundant), (e) `policy_decision.decision is not BLOCK` (not overridable), (f) `APPROVE requires proposed_destination_category is not None`. All six checks raise `InvalidHumanReviewError` on failure. The parametrized test `test_non_review_policy_outcome_is_rejected` covers AUTO+BLOCK x APPROVE+SKIP (4 combinations). The structural linkage tests cover mismatched proposal_id, file_id, and destination_category.

2. **Structural linkage prevents cross-object confusion.** The engine cross-validates `policy_decision.proposal_id` vs `proposal.id`, `policy_decision.file_id` vs `proposal.file_id`, and `policy_decision.destination_category` vs `proposal.proposed_destination_category`. An unrelated PolicyDecision/FileProposal pair cannot produce a valid HumanReviewDecision. The tests prove each field independently.

3. **Provenance is self-contained.** `HumanReviewDecision` carries `policy_engine_id` (from PolicyDecision), `proposal_engine_id` (from FileProposal), and `human_review_engine_id` (from rules.py). The `human_review_recorded_event()` function takes only the review -- no second/third parameter through which unrelated objects could be paired. The persistence round-trip test proves all provenance fields survive serialization.

4. **Domain model invariants are sound.** Frozen model, extra fields forbidden, UUID identity, timezone-aware UTC `reviewed_at` (with normalization), non-empty engine IDs, non-empty note (when provided), enum serialization. The domain test file covers all these cases.

5. **Zero filesystem I/O -- verified.** The AST guardrail (`test_no_filesystem_access.py`) checks every `.py` in `src/file_agent/human_review_engine/` for forbidden imports (`os`, `shutil`, `io`) and forbidden calls (`open`, `stat`, `resolve`, `exists`, etc.). The engine imports only `collections.abc`, `datetime`, and `file_agent.domain` modules.

6. **Statelessness is documented and proven.** The module docstring explicitly states: "Stateless and persistence-free by design: it cannot itself enforce 'one effective HumanReviewDecision per PolicyDecision' across separate calls." The test `test_engine_has_no_memory_across_calls_for_the_same_policy_decision` proves the engine allows two contradictory reviews for the same policy_decision_id -- this is the gap, not a feature. The production obligation (one effective review per PolicyDecision) is documented as an application/orchestration-layer responsibility.

7. **No latest-timestamp-wins or UUID-ordering semantics.** The engine has no state, no persistence dependency, and no comparison logic. It records a decision and returns. There is no code path implementing supersession, revocation, or "latest wins." The test proves the engine's silence on this point.

8. **APPROVE is eligibility, not execution.** `HumanReviewDecision` with `outcome=APPROVE` is a recorded authorization fact. It does not trigger any filesystem mutation, does not create a TransactionRequest, and does not integrate with TransactionEngine. The docstring explicitly states: "APPROVE means the user explicitly approves the existing proposal for future execution -- it is NOT execution itself."

9. **SKIP is valid with or without destination.** A SKIP decision for an UNKNOWN/OTHER proposal with `destination_category=None` is valid. The engine does not require a destination for SKIP. The test `test_no_destination_proposal_skip_is_valid` proves this.

10. **Event semantics are correct.** `EventType.HUMAN_REVIEW_RECORDED`, `EntityType.HUMAN_REVIEW`, `entity_id=review.id`, `timestamp=review.reviewed_at`. The payload includes all lineage fields: `review_id`, `policy_decision_id`, `proposal_id`, `file_id`, `outcome`, `destination_category`, `policy_engine_id`, `proposal_engine_id`, `human_review_engine_id`, `reviewed_at`, `review_source`, `note`.

11. **No scope creep.** FA-009 did not introduce: TransactionEngine integration, execution of REVIEW, destination editing, rename, delete, Vault, Undo, UI, watcher, LLM approval, or persistence uniqueness mechanisms. The package is exactly: domain model + engine + rules + tests.

12. **No naming transformation.** The engine never modifies the filename. The `HumanReviewDecision` records the `destination_category` from the proposal, not a resolved path.

## Summary

FA-009 implements a durable human APPROVE/SKIP decision for PolicyDecision.REVIEW. The design is clean: the engine validates linkage/outcome rules, records the decision as an immutable domain fact, and remains intentionally stateless. The trust boundary is the application/orchestration layer, not the domain model. The AST guardrail proves zero filesystem I/O. The test suite covers all rejection paths, structural linkage, provenance, persistence, domain invariants, and the stateless duplicate gap. The minor issues -- manually-constructible domain model, missing None-destination persistence test, single-member enum -- are defensive documentation gaps that don't affect correctness or safety. The architecture is sound and the scope is properly bounded.
